Glosarium awal

LLM (large language model) adalah model bahasa berukuran besar yang memprediksi potongan teks berikutnya berdasarkan pola dari data latih; ia tidak memahami niat seperti manusia. Prompt adalah seluruh teks masukan yang dibaca model pada satu giliran, termasuk aturan, riwayat percakapan, dan dokumen tambahan. System prompt adalah bagian masukan dari pengembang yang berisi peran dan aturan asisten. Tool adalah fungsi yang boleh dipanggil model untuk bertindak di luar teks, misalnya mengirim surel atau mengubah data. Threat model adalah peta terstruktur tentang aset, aktor, alur data, dan cara sesuatu dapat salah. Batas kepercayaan adalah titik tempat data berpindah dari sumber yang kurang tepercaya ke komponen yang mengambil keputusan. Prompt injection adalah teks yang dirancang agar model mengikuti instruksi penyusup alih-alih aturan pemilik sistem. Sensitive information disclosure adalah keluarnya data rahasia atau pribadi melalui jawaban model. Insecure output handling adalah kebiasaan memakai keluaran model sebagai HTML, perintah, atau query tanpa validasi. Excessive agency adalah keadaan ketika sistem AI diberi fungsi, hak, atau otonomi melebihi kebutuhan tugasnya. Least privilege adalah prinsip memberi hak paling kecil yang cukup untuk menyelesaikan tugas. Allowlist adalah daftar eksplisit hal yang diizinkan; semua di luar daftar ditolak. Human-in-the-loop adalah desain yang mewajibkan manusia menyetujui langkah tertentu sebelum dijalankan. Redaksi adalah penyamaran bagian data sensitif, misalnya mengganti nomor identitas dengan penanda “[NIK disamarkan]”. Semua contoh pada modul ini memakai data sintetis dan organisasi fiktif.

1. Threat model fitur AI/LLM

Definisi dan tujuan

Threat model untuk fitur AI menjawab empat pertanyaan sederhana: apa yang sedang dibangun, apa yang dapat salah, apa yang akan dilakukan untuk mencegahnya, dan apakah langkah itu sudah cukup. Tujuannya bukan menebak semua serangan, melainkan memetakan aset (data dan aksi yang berharga), aktor (pengguna, pihak luar, administrator), serta setiap batas kepercayaan yang dilalui teks sebelum mencapai model atau tool. Hasilnya berupa daftar ancaman yang dapat diprioritaskan dan diuji.

Mengapa penting pada sistem nyata

Fitur AI jarang berdiri sendiri. Sebuah asisten biasanya menerima pesan pengguna, mengambil dokumen dari basis pengetahuan, membaca surel atau halaman web, lalu memanggil tool untuk mencari data atau mengubah catatan. Setiap sumber teks itu dapat berisi kalimat yang terdengar seperti perintah. Berbeda dengan aplikasi biasa, model tidak memiliki pemisah yang kaku antara “kode” dan “data”; semuanya dibaca sebagai teks. Karena itu kesalahan desain kecil, misalnya memberi asisten hak menghapus akun, dapat berubah menjadi insiden besar.

Mekanisme dan alur

Gambarkan alur data dari kiri ke kanan: pengguna → aplikasi pengatur (orchestrator) → model → tool → sistem tujuan. Tambahkan sumber konteks seperti dokumen, riwayat, dan basis data. Tandai garis putus-putus pada setiap perpindahan dari sumber tidak tepercaya. Untuk setiap panah, tanyakan: siapa yang menulis teks ini, apakah model akan menganggapnya instruksi, data apa yang ikut terbawa, dan aksi apa yang dapat dipicu. Kategori pada modul ini, yaitu injeksi langsung, injeksi tidak langsung, pengungkapan data, keluaran tidak aman, dan agensi berlebih, membantu memberi nama pada setiap panah yang berisiko.

Contoh aman dengan data sintetis

Program studi fiktif membuat chatbot FAQ mata kuliah. Asetnya adalah jadwal ujian, rubrik penilaian, dan daftar nilai. Aktornya mahasiswa, dosen, dan pihak luar yang dapat mengirim surel ke kotak masuk program studi. Dari peta alur terlihat bahwa daftar nilai tidak diperlukan untuk menjawab FAQ, sehingga tidak boleh masuk konteks. Chatbot juga tidak memerlukan tool apa pun selain pencarian FAQ. Dua keputusan desain ini menghapus dua kelas ancaman sebelum satu baris kode ditulis.

Contoh kerja langkah demi langkah · chatbot FAQ mata kuliah

  1. Tulis aset: jadwal (publik), rubrik (internal), nilai (rahasia).
  2. Gambar alur: mahasiswa → aplikasi → model → pencarian FAQ.
  3. Tandai batas kepercayaan: pesan mahasiswa dan dokumen unggahan.
  4. Untuk tiap batas, beri nama ancaman dan kontrol: nilai tidak masuk konteks; tidak ada tool tulis.
  5. Tentukan uji: pertanyaan tentang nilai teman harus dijawab “tidak tersedia”.

Kesalahpahaman dan failure mode

Kesalahpahaman umum adalah menganggap model “cukup pintar” untuk menolak permintaan jahat, sehingga threat model dilewati. Kesalahan lain ialah hanya memodelkan pesan pengguna dan lupa bahwa dokumen, hasil pencarian, atau keluaran tool juga masuk ke konteks. Ada pula tim yang menulis threat model sekali lalu tidak memperbaruinya ketika tool baru ditambahkan. Setiap tool baru adalah panah baru pada diagram dan harus dianalisis ulang.

Kontrol dan keterkaitan

Keluaran threat model adalah keputusan konkret: data apa yang boleh masuk konteks, tool apa yang tersedia, aksi apa yang membutuhkan persetujuan, dan kejadian apa yang dicatat. Pada minggu 5 Anda memetakan risiko aplikasi web/API dengan OWASP Top 10; minggu ini cara berpikir yang sama diterapkan pada fitur AI, dengan penekanan pada teks sebagai saluran instruksi. Konsep least privilege dan otorisasi dari minggu sebelumnya tetap berlaku: model hanyalah pengguna lain yang haknya harus dibatasi.

2. Prompt injection langsung dan tidak langsung

Definisi dan tujuan

Prompt injection terjadi ketika teks yang dikendalikan pihak lain berhasil mengubah perilaku model sehingga model mengikuti instruksi penyusup. Ada dua bentuk. Injeksi langsung berasal dari pengguna yang sedang bercakap dengan asisten, misalnya pesan yang mengklaim “aturan baru” atau “mode admin”. Injeksi tidak langsung berasal dari konten yang dibaca asisten atas nama pengguna, seperti dokumen, surel, ulasan, atau halaman web yang disisipi kalimat untuk asisten. Tujuan memahami keduanya adalah menempatkan kontrol di luar model, bukan berharap model selalu menolak.

Mengapa penting pada sistem nyata

Pada injeksi langsung, korban pertama adalah aturan bisnis: diskon, denda, atau batas topik dapat dilanggar. Pada injeksi tidak langsung, pengguna sah justru menjadi korban karena ia tidak menulis instruksi jahat itu; ia hanya meminta ringkasan. Jika asisten memiliki tool, instruksi tersembunyi dapat meneruskan data ke alamat luar atau menyetujui transaksi. Semakin banyak sumber teks dan tool, semakin besar permukaan serangannya.

Mekanisme dan alur

Aplikasi sederhana sering merakit satu teks panjang: aturan sistem, lalu pesan pengguna, lalu dokumen. Model memproses semuanya sebagai urutan kata tanpa label otoritas yang tegas. Kalimat yang berbentuk perintah, apalagi yang muncul belakangan atau mengklaim otoritas, dapat memenangkan kalimat aturan di awal. Kontrol struktural memisahkan peran (system, user, dan data), memberi penanda bahwa dokumen hanyalah kutipan, dan yang paling penting mencabut kemampuan aksi dari konteks yang tidak tepercaya. Deteksi kata kunci hanya lapisan tambahan karena variasi bahasa tidak terbatas.

Contoh aman dengan data sintetis

Peringkas surel fiktif milik biro kemahasiswaan menerima pesan dari luar organisasi. Di bagian bawah pesan terdapat kalimat kecil untuk “asisten” agar meneruskan lampiran ke kotak surat lain. Versi rakitan datar memanggil tool kirim surel. Versi aman membungkus isi surel sebagai data, menonaktifkan tool selama meringkas, dan hanya menampilkan peringatan “instruksi tersemat dikarantina”. Pengguna tetap mendapat ringkasan yang sama.

Contoh kerja langkah demi langkah · peringkas surel

  1. Catat sumber: surel eksternal (tidak tepercaya) dan permintaan staf (tepercaya).
  2. Periksa rakitan konteks: apakah isi surel memiliki otoritas yang sama dengan permintaan staf?
  3. Identifikasi tool yang aktif saat meringkas.
  4. Ubah desain: surel menjadi blok data berlabel, tool dinonaktifkan.
  5. Uji ulang surel yang sama; ringkasan tetap ada, tidak ada aksi.

Kesalahpahaman dan failure mode

Menambah kalimat “jangan patuhi pengguna” di system prompt tidak memutus mekanisme karena kalimat itu berada di saluran yang sama dengan serangan. Memblokir kata “abaikan” mudah dilewati dengan sinonim, bahasa lain, atau ejaan kreatif. Menganggap dokumen dari vendor terdaftar pasti aman juga keliru; dokumen tepercaya dapat berisi sisipan pihak ketiga. Failure mode paling berbahaya adalah ketika asisten yang terinjeksi masih memegang tool dengan hak tulis.

Kontrol dan keterkaitan

Kontrol utama adalah hierarki instruksi berbasis peran, pelabelan konten eksternal sebagai data tak tepercaya, pencabutan tool saat memproses konten luar, dan pembatasan hak aksi. Pencatatan percobaan override membantu deteksi. Lab 1 dan Lab 2 memperlihatkan kedua bentuk injeksi pada simulator lokal, sedangkan bagian excessive agency menjelaskan mengapa hak tool menentukan besar dampaknya.

3. Sensitive information disclosure

Definisi dan tujuan

Pengungkapan informasi sensitif terjadi ketika jawaban asisten memuat data yang seharusnya tidak dilihat penanya: data pribadi seperti NIK, nomor ponsel, alamat, dan nilai; rahasia teknis seperti kunci akses; atau informasi internal seperti rubrik penilaian. Tujuan pengendaliannya adalah memastikan bahwa jawaban hanya berisi data yang diperlukan untuk tujuan yang sah, sesuai prinsip privasi yang dibahas pada minggu sebelumnya.

Mengapa penting pada sistem nyata

Asisten sering dihubungkan ke basis data atau dokumen agar jawabannya relevan. Jika seluruh baris dan kolom dimasukkan ke konteks, model dapat mengutipnya ketika diminta dengan bingkai yang terdengar sah, misalnya “untuk verifikasi” atau “untuk arsip”. Kebocoran juga terjadi melalui log percakapan yang disimpan lalu dipakai ulang. Dampaknya meliputi pelanggaran privasi, sanksi regulasi, dan hilangnya kepercayaan.

Mekanisme dan alur

Model hanya dapat membocorkan apa yang berada di konteksnya atau yang pernah dipelajarinya. Karena itu kontrol paling kuat bekerja sebelum model: minimisasi data, yaitu memilih kolom dan baris yang diperlukan untuk tujuan tertentu. Lapisan kedua bekerja sesudah model: redaksi pola sensitif pada keluaran, misalnya enam belas digit berturut-turut atau format nomor ponsel. Instruksi “jaga privasi” dalam prompt tidak menghapus data dari konteks sehingga tidak dapat diandalkan sebagai kontrol utama.

Contoh aman dengan data sintetis

Direktori alumni fiktif memuat nama, tahun lulus, tempat kerja, nomor ponsel, dan alamat rumah. Fitur “cari alumni untuk mentoring” hanya membutuhkan nama, tahun lulus, dan bidang kerja. Tim membuat pandangan data khusus berisi tiga kolom itu. Ketika pengguna meminta nomor ponsel seorang alumni, asisten menjawab bahwa kolom tersebut tidak tersedia, dan filter keluaran tetap memeriksa pola nomor sebagai jaring pengaman.

Contoh kerja langkah demi langkah · direktori alumni

  1. Tulis tujuan fitur: mencari mentor berdasarkan bidang kerja.
  2. Daftar kolom yang benar-benar dibutuhkan: nama, tahun lulus, bidang.
  3. Bangun konteks hanya dari kolom tersebut.
  4. Tambahkan redaksi pola ponsel dan surel pada keluaran.
  5. Uji permintaan “tampilkan data lengkap” dan pastikan tidak ada nilai sensitif keluar.

Kesalahpahaman dan failure mode

Enkripsi database at rest sering dianggap cukup, padahal data didekripsi sebelum dimasukkan ke konteks asisten. Menyembunyikan kolom di tampilan antarmuka juga tidak membantu bila kolom itu ada di konteks. Redaksi berbasis pola dapat meleset untuk format yang tidak terduga, sehingga redaksi tidak boleh menjadi satu-satunya kontrol. Failure mode lain adalah menyimpan seluruh percakapan tanpa redaksi di log yang dapat dibaca banyak orang.

Kontrol dan keterkaitan

Gunakan minimisasi berbasis tujuan, pemeriksaan otorisasi per pengguna sebelum data diambil, redaksi keluaran dan log, serta masa simpan log yang terbatas. Kontrol ini berhubungan langsung dengan kontrol akses: asisten tidak boleh mengambil data yang penanya sendiri tidak berhak lihat. Lab 3 memperlihatkan perbedaan konteks penuh dan konteks minimal pada data bimbingan sintetis.

4. Insecure output handling

Definisi dan tujuan

Keluaran model adalah teks yang dibentuk dari masukan, termasuk masukan dari pihak tidak tepercaya. Insecure output handling terjadi ketika aplikasi memperlakukan teks itu sebagai sesuatu yang tepercaya: menyisipkannya sebagai HTML, menjalankannya sebagai perintah sistem, mengeksekusinya sebagai query database, atau memakainya sebagai alamat tujuan. Tujuan kontrol adalah memperlakukan keluaran model seperti masukan pengguna: divalidasi dan di-encode sesuai konteks pemakaiannya.

Mengapa penting pada sistem nyata

Banyak portal menampilkan jawaban asisten dalam format kaya agar tampak rapi. Bila jawaban memuat tag skrip atau tautan tipuan yang berasal dari dokumen yang diringkas, browser staf dapat menjalankannya. Fitur “tanya data” yang mengubah bahasa alami menjadi query juga berbahaya bila query dijalankan langsung dengan akun berhak penuh. Risiko ini menyambungkan dunia AI dengan kelemahan aplikasi web klasik seperti XSS dan injection.

Mekanisme dan alur

Rantainya: penyusup menyisipkan teks ke sumber data → model menyalin atau merangkai teks itu ke keluaran → aplikasi meneruskan keluaran ke interpreter (browser, shell, atau database) tanpa pemeriksaan → interpreter menjalankan instruksi. Kontrol memutus rantai di titik terakhir: tampilkan sebagai teks biasa atau lakukan encoding HTML; batasi format ke subset aman; untuk query, gunakan allowlist operasi, parameterisasi, dan akun baca-saja; untuk tautan, periksa skema dan domain terhadap daftar yang diizinkan.

Contoh aman dengan data sintetis

Portal pengumuman fiktif menampilkan ringkasan asisten memakai properti yang menafsirkan HTML. Sebuah pengumuman sumber berisi tag gambar dengan atribut peristiwa. Pada versi aman, portal menggunakan penulisan teks biasa sehingga tanda kurung sudut tampil sebagai karakter, bukan elemen. Tautan hanya dibuat untuk alamat internal yang lolos pemeriksaan pola. Tampilan tetap informatif, tetapi tidak ada kode yang dijalankan.

Contoh kerja langkah demi langkah · ringkasan yang dirender

  1. Temukan titik render keluaran asisten di antarmuka.
  2. Catat interpreter yang menerima keluaran: HTML, markdown, atau query.
  3. Ganti penyisipan HTML dengan penulisan teks atau encoding.
  4. Tetapkan allowlist tag dan skema tautan bila format kaya dibutuhkan.
  5. Uji ulang dengan keluaran sintetis yang memuat tag; pastikan tampil sebagai teks.

Kesalahpahaman dan failure mode

Kesalahpahaman paling umum adalah menganggap keluaran model aman karena “model kita sendiri”. Model tidak memiliki niat, tetapi ia dapat menyalin masukan jahat dengan setia. Meminta model “jangan hasilkan HTML” juga hanya harapan. Menyaring kata “script” saja mudah dilewati dengan atribut peristiwa atau variasi huruf. Failure mode lain adalah memberi akun database penuh pada fitur tanya-data.

Kontrol dan keterkaitan

Terapkan encoding kontekstual, validasi skema keluaran terstruktur, allowlist tag dan tautan, eksekusi dengan hak minimum, serta pengujian dengan keluaran sintetis berbahaya. Topik ini terkait langsung dengan validasi input dan kontrol injection dari minggu sebelumnya; perbedaannya, sumber data berbahaya kini melewati model sebelum sampai ke interpreter. Studi kasus pada tab 04 memuat dua skenario keluaran tidak aman untuk dilatih.

5. Excessive agency dan penggunaan tool

Definisi dan tujuan

Agen AI adalah asisten yang dapat merencanakan dan menjalankan tool secara berurutan untuk mencapai tujuan. Agensi berlebih muncul dalam tiga bentuk: fungsi berlebih (tool yang tidak diperlukan tetap tersedia), hak berlebih (tool berjalan dengan izin lebih luas dari kebutuhan), dan otonomi berlebih (aksi berdampak tinggi dijalankan tanpa konfirmasi). Tujuan kontrol adalah memastikan bahwa kesalahan atau manipulasi pada model tidak dapat langsung berubah menjadi kerusakan.

Mengapa penting pada sistem nyata

Model dapat salah paham, berhalusinasi, atau terinjeksi. Jika agen hanya dapat membaca, akibatnya terbatas pada jawaban yang salah. Jika agen dapat menghapus akun, mengubah peran, mengekspor data, atau mentransfer uang, satu tiket atau dokumen jahat cukup untuk menimbulkan insiden. Dampak ditentukan oleh hak yang dipegang agen, bukan oleh seberapa sopan permintaannya.

Mekanisme dan alur

Agen menerima tugas, menyusun rencana berupa daftar panggilan tool, lalu mengeksekusi. Titik kendali berada di antara rencana dan eksekusi. Gerbang tool memeriksa setiap panggilan terhadap allowlist tugas, mengklasifikasikan dampak (rendah, tinggi, kritis), menjalankan aksi rendah secara otomatis, menahan aksi tinggi dalam antrean persetujuan manusia, dan menolak aksi di luar tugas. Kredensial tool dibatasi scope-nya, misalnya hanya akun pada tiket tersebut dan hanya operasi baca.

Contoh aman dengan data sintetis

Agen kuota printer fiktif bertugas menjawab sisa kuota cetak mahasiswa. Versi awal diberi tool ubah_kuota dengan hak admin agar “lebih membantu”. Setelah threat model, tim menyadari tugasnya hanya membaca. Tool ubah_kuota dihapus dari allowlist; penambahan kuota menjadi formulir yang disetujui petugas. Permintaan “tambahkan kuota saya 500 lembar” kini menghasilkan draf pengajuan, bukan perubahan data.

Contoh kerja langkah demi langkah · agen kuota printer

  1. Daftar semua tool yang dimiliki agen dan dampaknya.
  2. Cocokkan dengan tugas: hanya cek_kuota yang dibutuhkan.
  3. Hapus tool lain dari allowlist; batasi kredensial menjadi baca-saja.
  4. Ubah aksi berdampak menjadi pengajuan yang menunggu persetujuan.
  5. Uji permintaan penambahan kuota; pastikan tidak ada perubahan data.

Kesalahpahaman dan failure mode

Meminta agen “berhati-hati” melalui prompt tidak mengubah hak aksesnya. Logging setelah eksekusi berguna untuk investigasi, tetapi akun yang sudah terhapus tidak kembali karena log. Memberi satu kredensial admin untuk semua tool demi kemudahan adalah pola yang paling sering menyebabkan dampak besar. Persetujuan manusia yang terlalu sering juga gagal karena petugas terbiasa menekan “setujui” tanpa membaca; persetujuan harus dibatasi pada aksi yang benar-benar berdampak dan menampilkan ringkasan yang jelas.

Kontrol dan keterkaitan

Kontrolnya adalah allowlist tool per tugas, kredensial least privilege, klasifikasi dampak, persetujuan manusia untuk aksi tinggi, batas laju, serta log keputusan. Konsep ini melanjutkan otorisasi dan least privilege dari minggu sebelumnya: agen diperlakukan sebagai subjek dengan hak sempit. Lab 4 memperlihatkan agen tiket helpdesk sebelum dan sesudah gerbang tool.

6. Human oversight, least privilege, validasi output, dan logging

Definisi dan tujuan

Human oversight adalah pengawasan manusia yang dirancang ke dalam sistem, bukan sekadar harapan bahwa seseorang akan memeriksa. Bersama least privilege, validasi output, dan logging, keempatnya membentuk lapisan pertahanan yang tetap bekerja walaupun model berhasil dimanipulasi. Tujuannya adalah membuat kegagalan model terlihat, terbatas dampaknya, dan dapat dipulihkan.

Mengapa penting pada sistem nyata

Tidak ada teknik yang menjamin model kebal terhadap prompt injection. Karena itu organisasi perlu berasumsi bahwa model suatu saat akan mengikuti instruksi yang salah. Pertanyaannya bergeser menjadi: apa yang dapat dilakukan model dalam keadaan terburuk, siapa yang akan menyadarinya, dan berapa cepat dampaknya dapat dibatalkan? Regulasi dan kebijakan institusi juga semakin menuntut adanya jejak audit dan penanggung jawab manusia untuk keputusan penting.

Mekanisme dan alur

Least privilege membatasi dampak: kredensial tool hanya untuk operasi dan data yang diperlukan. Validasi output membatasi jalur: keluaran diperiksa terhadap skema, format, dan allowlist sebelum dipakai. Human-in-the-loop membatasi otonomi: aksi berdampak tinggi masuk antrean dengan ringkasan yang dapat dipahami penyetuju. Logging memberi visibilitas: setiap keputusan penting (override terdeteksi, kolom ditolak, aksi ditahan, persetujuan diberikan) dicatat dengan waktu, aktor, dan alasan, tanpa menyimpan data sensitif secara utuh. Log ditinjau secara berkala dan dipakai untuk menyetel kontrol.

Contoh aman dengan data sintetis

Asisten beasiswa fiktif menyusun rekomendasi penerima dari berkas pendaftar. Asisten tidak dapat menetapkan penerima; ia hanya membuat draf peringkat beserta alasan. Draf masuk antrean persetujuan dua petugas. Log mencatat versi draf, petugas yang menyetujui, dan perubahan yang dilakukan manusia. Ketika ditemukan berkas yang berisi kalimat untuk memengaruhi asisten, peringatan di log membuat petugas memeriksa berkas itu secara manual.

Contoh kerja langkah demi langkah · antrean persetujuan beasiswa

  1. Tetapkan keputusan yang hanya boleh dibuat manusia: penetapan penerima.
  2. Batasi asisten pada draf peringkat dan alasan.
  3. Rancang tampilan persetujuan yang menunjukkan alasan dan peringatan.
  4. Catat setiap draf, persetujuan, dan perubahan di log audit tanpa data pribadi lengkap.
  5. Tinjau log mingguan untuk menemukan pola manipulasi.

Kesalahpahaman dan failure mode

Pengawasan manusia gagal bila penyetuju tidak diberi informasi cukup atau dibanjiri permintaan sehingga menyetujui semuanya. Log yang tidak pernah dibaca hanya menambah biaya penyimpanan, dan log yang menyimpan data pribadi utuh justru menjadi sumber kebocoran baru. Least privilege sering rusak perlahan ketika hak ditambah “sementara” lalu dilupakan. Validasi output yang hanya memeriksa panjang teks tidak menangkap isi berbahaya.

Kontrol dan keterkaitan

Tuliskan kebijakan keputusan mana yang wajib melalui manusia, tinjau hak tool secara berkala, validasi setiap keluaran terhadap konteks pemakaiannya, dan buat log yang terstruktur serta diredaksi. Keempat kontrol ini muncul pada tahap “pilih dan terapkan kontrol” di setiap lab. Studi kasus menilai kemampuan Anda memasangkan risiko dengan kontrol yang bekerja di luar model; ambang lulusnya minimal 60% skenario benar.

Empat lab terpandu: red-team exercise aman

Setiap lab mengikuti delapan tahap: prediksi → jalankan simulasi lokal → lihat perbedaan → pilih/terapkan kontrol → retest payload sama → observasi → sebab → kesimpulan. Asisten adalah simulasi berbasis aturan pada data sintetis; tidak ada layanan AI yang dihubungi.

Aturan API key (wajib)
  • Gunakan key gratis milik sendiri, misalnya Google AI Studio (Gemini) atau OpenRouter (model gratis). Pastikan sendiri panggilan dari browser berhasil sebelum deploy.
  • API key tidak boleh ditulis di kode atau di-commit ke repo. Halaman Anda publik; key yang tertulis di kode pasti bocor. Sediakan kolom isian key; simpan paling jauh di sessionStorage dan bungkus aksesnya dengan try/catch.

function simpanKey(v) { try { sessionStorage.setItem("p06-key", v); } catch (e) { /* sandbox */ } }
function bacaKey() { try { return sessionStorage.getItem("p06-key") || ""; } catch (e) { return ""; } }

// LLM asli (contoh Gemini). Untuk OpenRouter, sesuaikan URL, header Authorization, dan bentuk body.
async function llmAsli(prompt) {
  const key = document.getElementById("key").value || bacaKey();
  simpanKey(key);
  const url = "https://generativelanguage.googleapis.com/v1beta/models/" + LOG.model + ":generateContent";
  const res = await fetch(url, { method: "POST",
    headers: { "Content-Type": "application/json", "x-goog-api-key": key },
    body: JSON.stringify({ contents: [{ parts: [{ text: prompt }] }] }) });
  const data = await res.json();
  return data.candidates?.[0]?.content?.parts?.[0]?.text || "";
}

// KONTRAK: nama dan parameter jangan diubah. Bila pemeriksa memberi `model`, WAJIB dipakai.

  // VERSI AMAN: pasang kontrol DI LUAR model di sini (lihat teori), bukan sekadar menambah kalimat larangan.
  return { balasan: keluaran, aksi: [] };
};
